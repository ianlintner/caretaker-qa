### GHSA-24c4-3p7v-29cm — ianlintner/caretaker
_severity: **unknown**  •  source: osv_

### Summary

When reading a multipart part with `Content-Transfer-Encoding: base64`, `BodyPartReader.read_chunk()` kept reading until the chunk length was a multiple of 4, with no byte limit. A part with a short `Content-Length`, or a long run of whitespace, could cause the entire remaining body to be read into memory within a single call before any size check, or spin on the event loop.

### Impact

An attacker could bypass `client_max_size` to cause excessive memory use, or block the event loop, with a specially crafted multipart request to any handler that reads multipart data.

### GHSA-28qf-cpwq-vmc2 — ianlintner/caretaker
_severity: **unknown**  •  source: osv_

### Summary

When the pipelined request queue was full, the pure-Python parser stored the unparsed remainder internally and also returned it to the caller. After a handler declined an upgrade request, the buffered data was re-fed, so the buffer grew with each handled request and already-handled requests were dispatched to the application again.

### Impact

If users are using the Python parser (`AIOHTTP_NO_EXTENSIONS`, or not a standard wheel installed), an attacker could cause excessive memory use and cause pipelined requests to be processed more than once.

### Workaround

Switch to the default C parser.

### GHSA-3rp8-rxj8-mvjw — ianlintner/caretaker
_severity: **unknown**  •  source: osv_

### Summary

The `max_msg_size` check in the WebSocket reader added the declared frame length to the size of the partial message already buffered. In the C extension this addition is 64-bit arithmetic, so a declared length close to 2**63 overflowed and the check passed.

### Impact

An attacker could bypass `max_msg_size` and cause unbounded memory use by streaming an oversized WebSocket message after a small non-final fragment.

### Workaround

If unable to upgrade, the Python reader is unaffected and can be used with `AIOHTTP_NO_EXTENSIONS=1`.

### GHSA-h4cc-hm5h-fmm9 — ianlintner/caretaker
_severity: **unknown**  •  source: osv_

### Summary

When decompressing a payload made up of many concatenated compressed members (gzip, deflate or zstd), each member was decoded by passing the entire remaining input to a new decompressor, resulting in quadratic CPU time. Empty members produce no output, so `client_max_size` and output backpressure did not limit the work.

### GHSA-jm3w-gw2p-xjfj — ianlintner/caretaker

### Summary

`Application.add_domain()` compiled each `*` in a host mask to `[^:]*`. With two or more wildcards in a mask, matching a long `Host` header that does not match the mask took polynomial time on the event loop.

### Impact
